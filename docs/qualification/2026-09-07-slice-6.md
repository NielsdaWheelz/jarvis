## Delivered approval behavior

Every validated model-proposed Write first runs the existing fresh isolated,
empty-plan AutomaticWriteGate. Approval-required work is inserted as an
`awaiting_approval` action together with one host-owned approval `message` in a
single transaction. The originating model run returns a durable
`WaitingFor.user` suspension; no worker or provider session waits for the owner.

Host rendering supports only `gmail.send_draft` and Calendar
create/update/delete. It deterministically serializes the complete validated
stored arguments, canonical tool name, and action ID into one bounded UTF-8 JSON
text attachment. The component-bearing message identifies that complete
payload and includes only Approve and Deny. Missing renderers, malformed or stale
stored values, and incompatible contracts fail closed before functional
components are presented. Model prose, commentary, and preview text are never
used.

Opaque component IDs bind the decision, action, and internal approval-message
identity. The handler validates the configured owner, guild, channel, live
Discord message ID, durable relationship, and current state. Free-form or
relayed text never enters this path. Once a valid click arrives, Discord is
acknowledged and both components are disabled before slow work. Deny atomically
cancels and executes nothing. Approve atomically claims one executor; duplicates
and Approve/Deny races cannot duplicate an effect.

Gmail send stores the draft ID, known thread, complete normalized To/Cc/Bcc,
subject/body snapshot, and original draft-creation effect header. Immediately
before send, the known live draft must agree exactly. Reconciliation uses the
known draft first, then the known thread's bounded minimal/raw messages; it uses
no mailbox search, arbitrary-header query, or ordering assumption. One unique
exact effect-header/content match proves success only after all selected
candidates are processed. Multiple, conflicting, malformed, transient, or
partial evidence cannot. A repeat needs three complete absence observations,
safe repetition, and remaining immutable capacity. Timeout alone decides
nothing. Exhausted unresolved evidence becomes terminal `uncertain` and requests
owner inspection; it never executes automatically.

Shared, unknown-calendar, or attendee-bearing Calendar writes require approval.
Verified owner-only no-attendee writes remain automatic. Every changed value is
rendered from stored arguments. Calendar execution continues to use the
action-derived create identity and exact get-and-compare reconciliation.

After approval resolution, one idempotent host action-resolution message keyed
by action ID plus resolved state wakes a fresh run. It carries safe durable
evidence, not the model call ID. Missing approval delivery and missing resolution
rows are repaired at startup. Incompatible undelivered approvals are cancelled
and delivered inert; incompatible delivered prompts are disabled before
cancellation. An acknowledged Deny is disabled before its recovery resolution.
A visible model response or deterministic fallback is mandatory.

## Accepted trade-offs

- Approval adds human latency. Jarvis durably suspends and discards the provider
  session rather than holding a worker; completion therefore returns through a
  new host action-resolution turn and may use a deterministic fallback.
- Full approval arguments are durable private database state and are transmitted
  to the configured Discord channel in a host-generated attachment. This is
  necessary for exact owner review. Payloads above one million bytes fail closed.
- A valid interaction is acknowledged and components are disabled before slow
  connector work. A crash in that interval leaves an executing action for
  bounded startup reconciliation rather than an apparently clickable prompt.
- Approval has no expiry table or workflow timer. Current durable state and
  immutable contract compatibility reject stale components; the single owner
  decides when to act.
- Gmail send reconciliation deliberately pays up to 306 provider reads, 30
  seconds, and 16 MiB to avoid mailbox search and unsafe retry. Incomplete or
  ambiguous evidence sacrifices liveness for terminal uncertainty and owner
  inspection.
- The stable effect header is visible to Gmail and the recipient. It contains an
  action-derived opaque identity, not a credential or owner content.
- Two identical proposals remain two actions by design. There is no semantic
  deduplication or intent key; effect identity and atomic claim prevent duplicate
