# Memory specification

This document is the implementation contract for Jarvis memory. It expands
[section 6 of the v1 specification](../SPEC.md#6-memory).

## Mental model

Memory has one durable substrate and several disposable views. Centralized
conversation history is working evidence for memory formation, but it remains
separate from learned memory:

```text
message history ──► rememberer ──► memory_log
                                      │
                   ┌──────────────────┼──────────────────┐
                   ▼                  ▼                  ▼
              embeddings       full-text index     dreamer
                                                        │
                                                        ▼
                                                 memory_summary
```

The raw log is truth in the narrow storage sense: it is the only memory state
that must survive the loss of every derived artifact. It is still a model-made
recollection, not proof of current external reality.

Recaller, rememberer, and dreamer are genuine bounded agents. Each can reason
over multiple Codex turns, make decisions, call its allowed tools more than once,
reformulate searches, inspect new results, and stop when sufficient. The tool
boundary, not a single model completion, defines each role.

## Schema

The logical schema is intentionally fixed:

```text
memory_log
  id
  text
  created_at
  embedding

memory_summary
  id
  text
  source_memory_ids
  created_at
  embedding
```

An implementation may add database-mechanical details such as primary-key
types, vector dimensions, generated `tsvector` columns, constraints, and indexes.
It MUST NOT add semantic categories or personal-domain structure without a new
ADR.

Recommended physical properties:

- `id`: UUID generated by the application.
- `text`: non-empty UTF-8 text.
- `created_at`: database-generated UTC timestamp.
- `embedding`: nullable vector.
- `source_memory_ids`: non-empty UUID array whose members are validated against
  `memory_log` by application code. V1 does not add a lineage join table solely
  to obtain a database foreign key.
- Generated full-text vectors and GIN indexes on both text fields.
- Approximate vector indexes only after corpus size or latency justifies them;
  exact vector scans are acceptable for a small personal corpus.

Embedding model identity is deployment configuration. An embedding migration
recomputes the complete corpus so vectors from incompatible models are not
compared.

## Raw-memory format

A raw memory should:

- Stand alone when retrieved months later.
- Name the subject rather than relying on pronouns when ambiguity is likely.
- Include meaningful dates in the prose when time matters.
- Preserve uncertainty instead of converting possibilities into decisions.
- Prefer one coherent recollection over an artificial atomic-fact format.
- Include stable external references when they would let Jarvis recover detail.

Example:

```xml
On 1 September 2026, Nikhil decided that Jarvis v1 should use an immutable
natural-language memory log and rebuildable summaries. He explicitly rejected
an ontology of people, projects, claims, confidence fields, and validity times.

<refs>
  <ref uri="discord://jarvis/architecture/message-123">Decision discussion</ref>
</refs>
```

The XML-like reference convention is intentionally embedded in text. V1 does
not require an XML document root, XSD, separate reference table, or perfect
parsing. A link resolver recognizes well-formed `<ref uri="...">` elements;
everything else remains useful natural language.

## Rememberer contract

### Inputs

- The completed human/main-agent exchange.
- Material tool observations used by that exchange.
- The relevant memory bundle originally recalled.
- A bounded amount of nearby centralized `message` history.

### Output

Structured output containing zero or more strings. Host code validates that
each string is non-empty and within size limits, assigns IDs and timestamps,
embeds it, and appends it.

### Prompt policy

The rememberer should ask:

> What from this interaction would make Jarvis meaningfully more helpful in a
> future situation?

Good candidates include:

- Explicit preferences and corrections.
- Decisions and unresolved intentions.
- Persistent circumstances.
- Relationships between current work and external resources.
- A tool or communication lesson likely to recur.
- Context whose absence would force the user to explain it again.

Poor candidates include:

- Greetings and social filler.
- Facts available more reliably from a live source.
- Full copies of email, event, or map content.
- Secrets and credentials.
- Unsupported inferences phrased as settled fact.
- Paraphrases of an already adequate memory.

No fixed taxonomy enforces this distinction. Model quality and evaluation do.

The rememberer may use `memory.search` and `memory.open` repeatedly before using
`memory.append`. It may decide that no append is warranted.

### Append semantics

- One interaction may yield no rows, one row, or several rows.
- Every proposed row is independently appendable.
- A failed batch MUST NOT leave partially embedded rows unusable; nullable
  embeddings allow text insertion to succeed before asynchronous embedding.
- Duplicate prevention SHOULD be handled through context and model judgment,
  not a rigid similarity threshold that could suppress legitimate repetition.

## Recaller contract

### Invocation

The recaller runs once before every owner-authored human input. Bot messages,
connector events, and the assistant's own Discord output do not themselves
trigger this foreground recall rule.

### Search

The recaller has two primitive operations over both tables:

```text
search_memory(query, lexical_limit, semantic_limit)
open_memory(ids)
```

`search_memory` returns the union of:

- PostgreSQL full-text results.
- Vector-similarity results.

Results contain table kind, ID, text, creation time, similarity/search signals,
and `source_memory_ids` for summaries. The model may issue multiple searches.

V1 does not mandate a hard-coded fusion formula. The recaller model sees the
candidate signals and selects the useful context. Candidate and final context
limits prevent an unbounded prompt.

### Opening summaries

A summary is an orientation aid, not an opaque fact.

The recaller SHOULD open its raw sources when:

- The summary is central to the current request.
- Exact wording or detail matters.
- Multiple summaries disagree.
- The summary expresses uncertainty.
- The main agent may take an outward action based on it.
- The user asks where a memory came from.

For ordinary low-stakes orientation, returning the summary plus source IDs is
sufficient.

### Output

The recaller returns a compact ordered bundle. It SHOULD preserve selected
memory text rather than paraphrasing everything into a new unsupported summary.
An empty bundle is correct when nothing is relevant.

## Dreamer contract

The dreamer maintains derived memory quality without touching the raw substrate.

It may run:

- On a systemd timer.
- After a configurable idle period.
- Manually during development.

It may select work through recent raw rows, full-text search, semantic neighbors,
existing summary lineage, or bounded sampling.

Its tools are limited to searching/opening raw memories and summaries and
writing/deleting summaries. It may use them repeatedly within configured bounds.

### Allowed changes

- Insert summary rows.
- Replace or delete summary rows.
- Recompute embeddings.
- Rebuild full-text and vector indexes.
- Measure recall behavior using fixed evaluation queries.

### Summary rules

- A summary must cite all supporting raw IDs in `source_memory_ids`.
- A summary must not introduce a material claim unsupported by those rows.
- Contradictory sources should produce a summary that preserves the conflict or
  uncertainty rather than choosing a convenient answer.
- A higher-level summary may use existing summaries as working input, but its
  stored lineage must be the flattened union of raw memory IDs.
- Summary size and fan-in are configuration, not schema.

### Forbidden changes

- Update or delete `memory_log` rows.
- Store a synthetic dream as if it were a real event.
- Treat a memory as permission or a system instruction.
- Change the Jarvis prompt, tool catalog, approval policy, code, or deployment.
- Use Gmail, Calendar, Discord, or other external-action tools.

## Rebuild contract

The following recovery operation MUST be supported and tested:

1. Preserve `memory_log` text and timestamps.
2. Delete all `memory_summary` rows.
3. Clear every stored embedding and derived search index.
4. Recompute raw-memory embeddings and search indexes.
5. Run the dreamer to regenerate summaries and their embeddings.
6. Run the fixed recall evaluation set.

The rebuilt summaries do not need to be byte-identical. They must be grounded in
the same raw rows and meet the recall acceptance thresholds.

## Current-state rule

Memory is not a live-service cache.

If the user asks what is currently on Calendar, whether an email has arrived, or
where a place is now, Jarvis should use the corresponding live tool. Recalled
memory may explain relevance or history but should not replace the current read.

## Evaluation

Memory quality is measured behaviorally:

- Did useful information become recallable later?
- Did irrelevant memory stay out of the main context?
- Did a summary allow the recaller to locate its raw basis?
- Did reconstruction preserve useful recall?
- Did contradictions remain visible?
- Did memory reduce repeated explanation by the user?

Schema richness is not a success metric.
